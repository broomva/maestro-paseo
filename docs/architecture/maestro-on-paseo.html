Maestro on Paseo

How the Maestro design (apps/maestro/handoff/design_handoff_maestro) maps onto the Paseo plugin API, how data moves through the plugin as it is built today (apps/maestro-paseo at 9438e62), and what is missing. Written 2026-09-24 from the design docs, the plugin source and the @getpaseo/{plugin,client,protocol} 0.8.0 type definitions. The installed Paseo.app reports 0.9.2 in its Info.plist; host-side facts below marked "0.9 host" were read from its bundled code (Resources/app.asar and Resources/app-dist), not from the 0.8.0 types.

The articulation in one idea: two authorities and a binding

Paseo owns execution

Agents, sessions and their timelines, worktrees, providers and models, permission prompts, the relay and every device the app runs on. Maestro's design calls this the runtime, the relay and the clients. Paseo already is all three, so the plugin builds none of them.

Maestro owns intent and judgment

The work contract, the eight-state machine, the checks, the gate, the receipts and the unsupervised-hours ledger. All of it lives in plain files under the work root: _work.md is the contract and _events.jsonl is the append-only log. The files are the system of record, as the design requires.

The binding between them

Each dispatched run is a Paseo agent carrying the label maestro.work=<id> (an adopted session is bound by its id instead), and the item's dispatched event records its agent, workspace and branch. Paseo's hook events arrive keyed by agent id; the plugin routes them to the right folder through an in-memory index, and a reconcile pass repairs anything a missed hook left behind.

Everything that crosses the boundary is one of four things: an RPC from the app to the plugin, a facade call from the plugin into Paseo, a hook from Paseo into the plugin, or a direct host call from the app that never touches the plugin. There are two direct host calls today: answering a permission (client/detail.tsx:162) and listing projects in the new-work form (client/new-work.tsx:40-45). The first is where the allow-or-deny decision gets lost.

How data flows

━▶ RPC or direct call ━▶ plugin calling the Paseo facade ━▶ Paseo hook into the plugin ━▶ file and git writes ━▶ where information is dropped today
  1. Reading. The Maestro surface calls work.list every 4 seconds (client/plane.tsx:19, client/hooks.ts:22-27); the Work panel polls work.for-agent and the detail pane work.get at the same interval. The plugin scans every _work.md and its log from disk, and at most every 10 seconds (server/engine.ts:118) it asks Paseo about the agent bound to each item that is running or at review and not running its checks (server/engine.ts:931-957): refresh(), then timeline.refetch for a missed turn end. There is no push channel to the client and no persistent index (the design's SQLite); the list is recomputed from files each time, and an in-memory map from agent to folder routes hooks.
  2. Dispatch. work.dispatch → engine.dispatch → startRun (server/runs.ts:67-97): resolve the provider's default model; with isolation: worktree (the default) create a Paseo workspace as a worktree on a fresh run/<hex> branch (random hex, server/runs.ts:35-37), otherwise open the repository directory; then create one agent there with the composed brief and the label maestro.work=<id>. Only then is the item moved to running, under its per-item lock (_work.md is rewritten by temp file and rename, then _events.jsonl is appended). If recording fails, the engine tries to archive the agent and a worktree it created (server/engine.ts:350-379); both are best effort, so a run can outlive a failed dispatch.
  3. The run stops. Paseo fires agent.turn_ended with the outcome and the timeline. The plugin routes it by agent id, records the turn, and runs the item's checks in the run's directory (the worktree, or the repository itself in directory mode) with a minimal environment (server/checks.ts, in order, stopping at the first required failure). A completed turn under gate: human lands at review (Needs you); under gate: auto it closes unless a required check failed, in which case it is Stuck (shared/states.ts landingState, server/events.ts:134-137). A failed or canceled turn goes to Stuck.
  4. Permission. agent.permission_requested parks the item at Needs you as a question. The app answers by calling Paseo directly (client/detail.tsx:162), not through the plugin. Paseo then fires agent.permission_resolved with resolution: {behavior: "allow" | "deny", message?} (@getpaseo/plugin/dist/server/lifecycle.d.ts:59-63), but the plugin passes on only the request id (index.server.ts:42), so the receipts never say what you decided.
  5. The gate. work.verdict (shared/contracts.ts:147-151) records the verdict. Approve moves to Done, block to canceled, and send back returns to running and wakes the same session with your note (agents.ref(id).send). Approve and send back are refused while the session is visibly working or a permission question is open; block is not (server/engine.ts:413-418).

Also: /maestro and "Track this session in Maestro" adopt an existing Paseo session as work (adoptAgent); agent.turn_started and agent.archived keep the state honest when you continue a session by hand or archive it.

What is missing, grouped by what it would take

1. Buildable in the plugin today, with the API it already has

  • Record the permission decision (BRO-2573). Pass event.resolution through index.server.ts:42 and store it.
  • An overridden state for approving over a failed check; the data already knows.
  • Stage 0 and Stage 2 of the verifier. A diff and protected-path guard is a built-in check over git in the run's directory. A judge is a second agent on another provider in the same directory, returning a typed verdict through outputSchema.
  • Attempt caps and automatic send-back on failing checks, as engine policy.
  • Hook-triggered routines (the design's hook trigger) via server.on.
  • History and the system panel (see docs/prototypes/system-panel.html), behind one aggregate RPC.
  • A pending-decision cap, refused at dispatch. This is our proposal, not the design's; the design caps concurrent runs at 3 (build-docs/specs/ORCHESTRATOR.md:37).
  • Kill and stop conditions, through archive(), and budgets for runs on a plugin-registered provider. Neither has been tried.

2. In Paseo, but not on the plugin facade

A non-destructive cancel (cancelAgent), switching mode or model, schedules (so: cron routines, the tick and the orchestrator), checkout, PR and merge (so: approve that lands the branch), and file access all exist on DaemonClient and the paseo CLI. A plugin can reach them only by shelling out to the CLI or by importing the client's internal module as a runtime dependency, both unverified and both coupled to internals. The clean path is asking Paseo to widen the facade.

3. Needs the host

Notifications to a closed laptop or a phone, and real charts (SVG or canvas).

4. Deliberately different

Send back wakes the same session instead of a fresh run; approve does not merge; queued or stuck work can be canceled directly; existing sessions can be adopted; the run branch is shown in the detail pane where the design hides worktrees.

5. Not built anywhere yet

Several items are also missing from Maestro's own app (apps/maestro/apps/app): the wake log, the kill button, the mobile shell, notifications, the dispatch rail, and real data behind the knowledge graph and settings. Missing from the plugin is not the same as present in Maestro.
