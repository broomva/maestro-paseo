Maestro on Paseo

How the Maestro design (apps/maestro/handoff/design_handoff_maestro) maps onto the Paseo plugin API, how data moves through the plugin as it is built today (apps/maestro-paseo at 9438e62), and what is missing. Written 2026-09-24 from the design docs, the plugin source and the @getpaseo/{plugin,client,protocol} 0.8.0 type definitions, with the installed host at 0.9.1.

The articulation in one idea: two authorities and a binding

Paseo owns execution

Agents, sessions and their timelines, worktrees, providers and models, permission prompts, the relay and every device the app runs on. Maestro's design calls this the runtime, the relay and the clients. Paseo already is all three, so the plugin builds none of them.

Maestro owns intent and judgment

The work contract, the eight-state machine, the checks, the gate, the receipts and the unsupervised-hours ledger. All of it lives in plain files under the work root: _work.md is the contract and _events.jsonl is the append-only log. The files are the system of record, as the design requires.

The binding between them

Each run is a Paseo agent carrying the label maestro.work=<id>, and the item's dispatched event records its agent, workspace and branch. Paseo's hook events arrive keyed by agent id; the plugin routes them to the right folder through an in-memory index, and a reconcile pass repairs anything a missed hook left behind.

Everything that crosses the boundary is one of four things: an RPC from the app to the plugin, a facade call from the plugin into Paseo, a hook from Paseo into the plugin, or a direct host call from the app that never touches the plugin. Permissions are the only case of the last kind today, and that is where the allow-or-deny decision currently gets lost.

How data flows

━▶ RPC or direct call ━▶ plugin calling the Paseo facade ━▶ Paseo hook into the plugin ━▶ file and git writes ━▶ where information is dropped today
  1. Reading. Each open Maestro surface calls work.list every 4 seconds (client/hooks.ts:22-27). The plugin scans every _work.md and its log from disk, and at most every 10 seconds (server/engine.ts:118) it asks Paseo about each bound agent (agents.ref(id).refresh(), then timeline.refetch for a missed turn end) so a hook it missed while stopped is recovered. There is no push channel to the client and no index; the list is recomputed from files each time.
  2. Dispatch. work.dispatch → engine.dispatch → startRun (server/runs.ts:69-96): resolve the provider's default model, create a Paseo workspace as a worktree on a fresh run/<id> branch, and create one agent in it with the composed brief and the label maestro.work=<id>. Only then is the item moved to running, under its per-item lock (_work.md is rewritten by temp file and rename, then _events.jsonl is appended). If recording fails, the agent and the worktree are archived, so no run exists that the files do not know about.
  3. The run stops. Paseo fires agent.turn_ended with the outcome and the timeline. The plugin routes it by agent id, records the turn, runs the item's checks inside the worktree with a minimal environment (server/checks.ts), and moves the item to review (Needs you). Under gate: auto, passing checks close it and failing checks leave it Stuck.
  4. Permission. agent.permission_requested parks the item at Needs you as a question. The app answers by calling Paseo directly (client/detail.tsx:162), not through the plugin. Paseo then fires agent.permission_resolved with resolution: {behavior: "allow" | "deny", message?} (@getpaseo/plugin/dist/server/lifecycle.d.ts:59-63), but the plugin passes on only the request id (index.server.ts:42), so the receipts never say what you decided.
  5. The gate. work.decide records the verdict. Approve moves to Done, block to canceled, and send back returns to running and wakes the same session with your note (agents.ref(id).send). A verdict is refused while the session is visibly working, or while a permission question is open.

Also: /maestro and "Track this session in Maestro" adopt an existing Paseo session as work (adoptAgent); agent.turn_started and agent.archived keep the state honest when you continue a session by hand or archive it.

What is missing, grouped by what it would take

1. Buildable in the plugin today, with the API it already has

  • Record the permission decision (BRO-2573). Pass event.resolution through index.server.ts:42 and store it.
  • An overridden state for approving over a failed check; the data already knows.
  • Stage 0 and Stage 2 of the verifier. A diff and protected-path guard is a built-in check over git in the worktree. A judge is a second agent on another provider in the same worktree, returning a typed verdict through outputSchema.
  • Attempt caps and automatic send-back on failing checks, as engine policy.
  • Hook-triggered routines (the design's hook trigger) via server.on.
  • History and the system panel (see docs/prototypes/system-panel.html), behind one aggregate RPC.
  • The pending-decision cap, refused at dispatch.

2. In Paseo, but not on the plugin facade

Kill (cancelAgent), switching mode or model, schedules and heartbeats (so: cron routines, the tick and the orchestrator), checkout, PR and merge (so: approve that lands the branch), and file access all exist on DaemonClient and the paseo CLI. A plugin can reach them only by shelling out to the CLI or by importing the client's internal module as a runtime dependency, both unverified and both coupled to internals. The clean path is asking Paseo to widen the facade.

3. Needs the host

Notifications to a closed laptop or a phone, real charts (SVG or canvas), and budgets enforced in the request path of every model call. The last one is structural: without a hook on model calls a plugin can observe spend but never refuse it, which means the design's rule that nothing runs unattended without a budget guard cannot be met by a plugin alone.

4. Deliberately different

Send back wakes the same session instead of a fresh run; approve does not merge; queued or stuck work can be canceled directly; existing sessions can be adopted; the run branch is shown in the detail pane where the design hides worktrees.

5. Not built anywhere yet

Several items are also missing from Maestro's own app (apps/maestro/apps/app): the wake log, the kill button, the mobile shell, notifications, the dispatch rail, and real data behind the knowledge graph and settings. Missing from the plugin is not the same as present in Maestro.
