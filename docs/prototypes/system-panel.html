Maestro · system panel prototypes

Six ways to show the whole system on one panel of the Maestro plugin page. Every mark is a positioned box, dot or line of text: no SVG, no canvas, no CSS grid, no pseudo-elements, no calc() and no percentage transforms. The 0.8.0 client SDK hands a plugin React Native components (its react-native and ui entries) and no SVG or canvas component, so what is drawn here should port to <View>s with percentage positions, the way the "Unsupervised today" track already works. Hover here stands in for press in the app. All data on this page is synthetic.

What building these turned up

  1. The receipts drop whether a permission was allowed or denied, though Paseo sends it. The host's agent.permission_resolved hook carries resolution: {behavior: "allow" | "deny", message?} (@getpaseo/plugin/dist/server/lifecycle.d.ts:59-63), but the plugin passes on only the request id (index.server.ts:42) and records only that (server/engine.ts:837-843). Passing event.resolution through and storing it makes the permissions view show what you granted (BRO-2573).
  2. The host's status colors cannot carry meaning alone. Measured with validate_palette.js from the dataviz skill bundled with Claude Code 2.1.280, on the status colours read from the installed Paseo.app on 2026-09-24 (light: success #3e704a, warning #7b5d39, danger #9d433b; dark: #6cb17b, #c09664, #d8847b). Under simulated deuteranopia, warning and danger are ΔE 0.5 apart in light mode, and pass and fail are ΔE 3.2 (light) and 1.1 (dark); the validator's target is ΔE 8 (OKLab × 100). So status here is carried by a shape or glyph and, wherever the mark has room, a word: a passed check is a circle, a failed one a square, a timeout a triangle, and swimlane and check-grid rows end in a labelled state. Treemap cells show the glyph when words do not fit and colour alone below 14px square, so small cells are read in the treemap's table view.
  3. Approving over a failed check has no state of its own. The data already knows (the last checks.finished before the approving gate has a failure), so every view here can mark it. Today the list shows it as a green Done dot; the detail pane shows it only in small grey type ("1 of 1 check failed · you approved") above a red failed-check row. This prototype proposes a state of its own (Overridden), and labels canceled work Canceled in rows where the plugin's list groups it under Done.
  4. work.list does not return events. The swimlanes, attention, check and permission views need the event logs of every item. One aggregate RPC (for example work.timeline, reusing runningIntervals from server/events.ts) avoids calling work.get per item. The flow board needs only what work.list already returns plus the time each item entered its state. The treemap also needs each item's accumulated running time, which work.list does not return, so the aggregate RPC has to carry it.
  5. The pending-decision cap is a rule, not a picture. The flow board draws it, but "dispatch pauses when three items need you" has to be enforced in the engine's dispatch path to mean anything.
